# 批量重命名时 002 排在 001 前面：sorted() 排的不是时间

## 元信息

| 项 | 内容 |
|---|---|
| 日期 | 2026-10-29 |
| 耗时 | 发现到修好约 15 分钟 |
| 环境 | Windows / Python 3.12.10 |
| 来源 | 自己写的 `projects/scripts/rename.py`，跑完看输出觉得不对劲 |
| 关键词 | `sorted` `os.listdir` 批量重命名 排序 |

## 一、现象

给脚本加了“按修改日期重命名”之后，跑出来的序号和日期是错位的：

```
2026-08-03-002.jpg     ← 8 月的文件拿到了 002
2026-09-15-001.jpg     ← 9 月的文件拿到了 001
2026-10-29-003.jpg
```

文件确实改名成功了，日期也是对的。**没有报错，程序正常退出**——只是顺序“看着别扭”。

## 二、排查思路

1. **先排除日期读错**：把其中两个文件的修改时间分别改成 8 月和 9 月，重跑 `--dry-run`。日期输出正确 → 说明 `os.path.getmtime()` 和 `strftime()` 没问题。
2. **再排除计数逻辑**：`count` 每处理一个文件加 1，逻辑本身没错——错的是“谁先被处理”。
3. **关键观察**：拿到 002 的是 8 月的文件，拿到 001 的是 9 月的。说明**序号是按文件名顺序发的，不是按时间**。
4. **回头看出问题的那一行**：

   ```python
   files = sorted(os.listdir(args.folder))
   ```

   `os.listdir()` 返回文件名列表，`sorted()` 对**字符串**排序——排的是名字的字典序，不是修改时间。

## 三、根因

`sorted(os.listdir(...))` 按**文件名字典序**排序。所以 `demo-001.jpg` 永远排在 `demo-002.jpg` 前面，序号就跟着文件名走，和真实日期无关。

改日期只改变了“日期部分”，没有改变“谁先谁后”。

## 四、修法

```diff
- files = sorted(os.listdir(args.folder))
+ files = sorted(
+     os.listdir(args.folder),
+     key=lambda n: os.path.getmtime(os.path.join(args.folder, n)),
+ )
```

`key=` 告诉 `sorted()`：**别按元素本身排，按这个值排**。这里按每个文件的修改时间戳排。

## 五、验证

不能只看“跑完没报错”。做法是先演练，看序号是不是真的翻转：

```
[演练] 2026-08-03-002.jpg  ->  2026-08-03-001.jpg      ← 从 002 变成 001
[演练] 2026-09-15-001.jpg  ->  2026-09-15-002.jpg      ← 从 001 变成 002
[演练] 2026-10-29-003.jpg  ->  2026-10-29-003.jpg      ← 位置本来就对，不变
```

三个位置对了两个，第三个不变——这正是**幂等**的表现：位置对的就不动。

确认无误后再真跑，用 `Get-ChildItem` 核对磁盘上的文件名。

## 六、预防

- 批量操作前先问一句：**“我按什么排序？这个依据稳定吗？”**
  文件名、`os.listdir()` 的返回顺序、字典序——都不等于“业务上想要的那个顺序”。
- 涉及顺序的地方，先用 `--dry-run` 打出来看一眼再执行。
- **结果“看着别扭”就停下来查。** 不报错的 bug 比报错的危险得多：报错会拦住你，不报错会安静地把错误结果交给你。

## 一句话

排序依据错了，程序不会报错，只会安静地给你一个错的顺序。
