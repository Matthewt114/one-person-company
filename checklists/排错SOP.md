# 排错 SOP（我的版本）

> 第 3 周的任务：把这张表填完。**每条规则后面必须有一句你自己的话**，抄书上的不算。
> 填完之后，每次修东西都照着走；走过三次以上，这张表才算你的。

---

## 使用方式

1. 遇到问题，先打开这张表，从第一条往下走，**不许跳**。
2. 每走一步，在下面记一行：时间、做了什么、结论。
3. 结束后回填"哪一步最关键""哪一步浪费了时间"。

---

## 九条规则

### 1. 了解你的系统
不要一上来就改代码。先搞清楚：正常情况下它应该怎么工作、数据怎么流动、各模块怎么交互。

- 我的版本：动手之前先跑一遍"正常情况"，把正常的样子记下来——不然出了问题，我没有对照，连"哪里不对"都说不清。
- 具体动作：先什么都不改，完整走一遍流程，把每一步的输入和输出抄到 `log/blocked.md` 里，当成基线。

### 2. 让它失败
能稳定复现的 bug 才好修。先想办法让问题必然出现，而不是碰运气等它偶发。

- 我的版本：bug 复现不出来，我就没法判断到底修好没有——改完没崩，可能只是这次没触发。
- 具体动作：先找到一个必定出错的输入，写成 3 行以内的最小脚本（或 3 步操作），每次跑都报同样的错。

### 3. 别猜，去看
停止"我觉得可能是这里"。加日志、加断点、看真实的运行时数据。

- 我的版本：我脑子里冒出的"可能是……"十次有八次是错的，猜下去只会在错的地方浪费一小时。
- 具体动作：每次想说"可能是"的时候，先停下，在那一行前后各加一条打印，把真实的值打出来再判断。


### 4. 分而治之
把系统切成小块，用二分法定位问题在哪一半，反复缩小范围。

- 我的版本：200 行代码里肉眼找 bug 是浪费时间，必须切成能排除掉的两半。
- 具体动作：先注释掉后半段跑一次，问题还在就说明在前半段；再对半切，三四次就锁定了。

### 5. 一次只改一处
同时改多个地方，出了问题你不知道是哪个改动造成的。

- 我的版本：同时改三个地方，改好了我不知道是哪个起的效，改坏了也不知道是哪个搞的。
- 具体动作：改一处 → 跑一次 → commit 一次，commit message 写清"这次只改了什么"。

### 6. 保留审计线索
记录你改了什么、什么时候改的、结果如何。

- 我的版本：改到第三个小时，我早忘了前面试过什么，然后会把已经排除的改法再试一遍——这是纯浪费。
- 具体动作：动手前先在 `log/blocked.md` 加一行"开始改 X"；每改一次追加一行：时间、改了什么、结果（好了 / 没好 / 更糟）。

### 7. 检查插头
最傻的原因往往最常被忽略：环境变量没配、依赖版本不对、缓存没清、连错了数据库。

- 我的版本：最蠢的原因最容易被跳过，因为"这么基础的不可能错"——可十次里有六次就是它，我只是不想承认。
- 我的"插头清单"：
  - [ ] 运行的是我以为的那个文件吗？
  - [ ] 虚拟环境 / 解释器版本对吗？
  - [ ] 依赖装了吗，版本对吗？
  - [ ] 缓存清了吗？
  - [ ] 连的是本地还是线上？
  - [ ] 端口 / 权限 / 路径对吗？

### 8. 找个人看看（获取新视角）
求助时不要只说"你帮我看看是什么原因"，要说清六件事：

1. 正常应该怎样工作
2. 实际发生了什么
3. 什么条件下出现
4. 已经排除了哪些可能
5. 哪些结论有数据支持
6. 当前最不确定的环节是什么

- 我的版本：我盯两小时看不出来，不是眼睛不够用，是我"知道"它应该怎样，所以看不见它实际怎样。别人没有这个包袱。
- 求助模板：见上面六条，复制粘贴改。

### 9. 没有验证，就不算修好
故障消失 ≠ 问题解决。它可能只是触发条件没出现、概率下降、问题转移到别的环节、被保护掩盖、测试时间不够、或者修改产生了新副作用。

**A-B-A 验证模板：**

| 步骤 | 做什么 | 结果 |
|---|---|---|
| A | 原状态下复现故障 | 复现了吗？几 次 / 几 分钟内？ |
| B | 应用修改后，同样条件再跑 | 跑了几次？多久？故障还在吗？ |
| A | 恢复原状态，再跑一次 | 故障又出现了吗？ |

> 做不了 A-B-A 的时候（比如线上环境不能回滚），写清为什么做不了，以及你用什么替代证据。

- 我的版本：报错不见了，我会默认"修好了"。但我分不清"真的修好"和"这次没触发"——而客户分得清。
